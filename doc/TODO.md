## 1. 总体目标与架构约束

DataFactory 面向工业算法及工业时序模型测试，提供可扩展的组件化建模、组态构建、快速离线仿真和实时闭环供数能力。

### 1.1 两种核心运行形态

- [ ] **Studio：交互式组态与快速仿真工作台**
  - 加载、编辑和校验 YAML 组态。
  - 尽可能快地推进仿真时间，不等待物理世界时间。
  - 展示趋势、变量变化和仿真结果，帮助用户判断数据是否稳定、是否符合预期特征及测试需求。
  - 支持快速调整参数、重新运行和导出数据集。
  - Studio 的主要价值是组态设计、数据观察和快速验证，不承担 Runtime 的长期运行职责。

- [ ] **Runtime：独立运行与实时供数服务**
  - 不依赖 Studio 前端，可以通过 CLI 或服务方式启动。
  - 读取一份或多份 YAML 组态并独立运行。
  - 使用与 Studio 相同的组件定义和核心模型计算逻辑。
  - 按照物理世界时间推进仿真周期。
  - 内置 OPC UA Server，向外部工业算法/推理系统发布过程变量，并接收外部写入。
  - 支持持续运行、运行监控、异常处理和数据留存。

### 1.2 必须保持的架构原则

- [ ] Studio 与 Runtime 共享同一套模型定义、组件实现、Compiler 和核心 Engine，不复制或维护两套仿真逻辑。
- [ ] 运行模式差异由时间调度器、数据接口和运行宿主提供；核心组件计算语义保持一致。
- [ ] YAML 是标准化组态载体：既可以由工程师编写，也可以由 AI Agent 根据产品说明书、组件知识和 Skill 生成。
- [ ] AI Agent 负责理解需求和构建组态，不负责替代 DataFactory Engine 执行仿真。
- [ ] 新增组件允许修改组件定义、Compiler 和 Engine 对应代码；不以动态插件加载或完全不修改核心代码为前提。
- [ ] 当前测试任务的被测算法不作为该任务自身的数据生成组件；当某算法在另一个测试任务中承担被测对象的运行环境或关联模型角色时，才可以作为该场景的组件。
- [ ] 离线数据集回放可以作为补充能力，但不是 Runtime 的核心实时运行方式；实时模式必须直接执行模型并支持 OPC UA 闭环写入。

## 2. P0：共享执行核心与运行模式解耦

### 2.1 现状梳理与架构边界

- [ ] 梳理当前 Rust Engine、Compiler、Studio Go/Wails 后端及前端之间的调用链。
- [ ] 明确模型编译结果、组件运行状态、虚拟时钟、变量存储和数据采集的所有权。
- [ ] 识别 Studio 专属代码与可供 Runtime 复用的核心代码。
- [ ] 形成核心模块边界和依赖图，避免 Runtime 依赖 Wails、React 或 Studio UI。

### 2.2 统一模型执行接口

- [ ] 将“单个仿真周期的模型推进”定义为统一执行入口。
- [ ] 将时间推进策略从组件计算逻辑中分离。
- [ ] 定义统一的模型初始化、单周期执行、变量读取/写入、状态快照及停止接口。
- [ ] 明确组件内部状态在连续周期之间的维护规则。
- [ ] 明确表达式计算、Slot/变量映射和组件间数据传递的执行顺序。
- [ ] 保证 Studio 快速仿真和 Runtime 实时仿真使用相同的单周期计算逻辑。

### 2.3 双时间运行机制

- [ ] 定义仿真时间（Simulation Time）与宿主机真实时间（Wall-clock Time）的关系。
- [ ] **Fast/Offline 模式：** 按仿真周期连续推进，不等待真实时间；支持快速生成长周期数据。
- [ ] **Realtime 模式：** 按配置周期映射到真实时间，执行周期调度和节拍控制。
- [ ] 定义实时周期超时、计算耗时超过周期、落后追赶、跳周期及异常恢复策略。
- [ ] 记录仿真时间、真实时间、周期序号和实际执行耗时，便于诊断时序偏差。
- [ ] 验证同一 YAML、相同初始条件下，Fast 与 Realtime 模式的模型计算结果遵循相同的周期语义；允许真实执行时间和调度抖动不同。

**验收标准**

- [ ] 同一份 YAML 能分别由 Studio/Fast 模式和 Runtime/Realtime 模式运行。
- [ ] Fast 模式不因配置的仿真周期而等待真实时间。
- [ ] Realtime 模式按设定周期推进，并能识别和报告周期超时。
- [ ] 两种模式没有各自维护一套组件计算实现。

## 3. P0：Runtime CLI 与多组态独立运行

### 3.1 CLI 运行入口

- [ ] 提供独立 Runtime 可执行程序，不要求启动 Studio。
- [ ] 支持指定 YAML 配置路径。
- [ ] 支持启动、停止、优雅退出及退出码。
- [ ] 支持指定运行模式、运行周期、实例名称和必要的运行参数。
- [ ] 提供配置预检查/编译检查命令，使组态可以在正式启动前验证。
- [ ] 输出结构化日志，记录配置加载、编译、初始化、运行、停止和异常。

### 3.2 多 YAML / 多实例运行

- [ ] 支持一个 Runtime 管理进程启动多份独立 YAML 组态。
- [ ] 每个实例拥有独立的模型状态、虚拟时间、周期调度和运行状态。
- [ ] 为每个实例配置唯一实例标识及 OPC UA 地址空间隔离策略。
- [ ] 明确实例之间是否允许数据连接；默认保持隔离，跨实例连接如有需要再单独定义。
- [ ] 支持单实例停止、重启和故障隔离，避免一个实例异常导致其他实例无条件退出。
- [ ] 明确多实例资源限制及 CPU/内存监控策略。

**验收标准**

- [ ] 不启动 Studio，仅通过 CLI 即可运行一份 YAML。
- [ ] 同一 Runtime 进程可以启动多份 YAML，并验证实例状态互不污染。
- [ ] 一个实例发生配置错误或运行异常时，其他实例按设计继续运行或按明确策略停止。

## 4. P0：OPC UA 实时发布与闭环写入

> 这是 Runtime 区别于单纯离线数据生成器的核心能力。OPC UA 不只是把预先生成的数据播放出去，而是与正在运行的模型计算形成双向闭环。

### 4.1 OPC UA Server 基础能力

- [ ] 在 Runtime 中集成 OPC UA Server。
- [ ] 支持配置 Server Endpoint、Namespace、实例标识和节点组织方式。
- [ ] 将模型变量映射为 OPC UA 节点。
- [ ] 支持配置变量的数据类型、读权限、写权限及必要的初始值。
- [ ] 支持客户端连接、读取、订阅和断开重连。
- [ ] 为节点提供正确的数据类型、Source Timestamp、StatusCode/质量状态。
- [ ] 明确 OPC UA 安全策略、用户认证、证书信任及部署配置；至少形成可用于隔离测试环境的安全配置方案。

### 4.2 模型变量与 OPC UA 节点映射

- [ ] 定义 YAML 中变量到 OPC UA NodeId 的映射规则。
- [ ] 支持区分只读输出变量、可写输入变量及内部变量。
- [ ] 对不允许外部写入的变量拒绝写操作。
- [ ] 对写入值执行数据类型、范围和状态校验。
- [ ] 定义节点命名、命名空间和多实例 NodeId 冲突避免规则。
- [ ] 提供映射配置错误的预检查及清晰错误信息。

### 4.3 闭环写入与周期一致性

- [ ] OPC UA 写入必须更新模型运行时使用的变量，而不是只修改 OPC UA 节点的显示值。
- [ ] 定义外部写入进入模型计算的生效边界：采用明确的周期边界/输入快照规则，避免在组件计算过程中并发修改变量。
- [ ] 定义一个周期内多次写入同一变量时的处理规则，例如按接收顺序保留最新有效值，并记录写入信息。
- [ ] 定义写入值与模型内部计算值之间的变量所有权和冲突处理策略。
- [ ] 明确一次周期的顺序：接收并提交外部输入、执行模型计算、更新输出变量、发布 OPC UA 数据。
- [ ] 外部写入的值必须能够影响后续组件计算和后续周期的过程响应。
- [ ] 记录写入时间、目标变量、写入来源、结果和实际生效周期，便于问题追溯。
- [ ] 对断连、迟到写入、非法写入、周期超时和运行停止定义明确行为。

### 4.4 端到端闭环验收

- [ ] 建立一个包含水箱、阀门及控制逻辑的实时闭环案例。
- [ ] 使用独立 OPC UA Client 读取 Runtime 发布的 PV/MV/SP 等变量。
- [ ] 从 OPC UA Client 写入控制量或设定值。
- [ ] 验证写入值进入 Runtime 当前模型变量，并在后续周期影响设备/过程计算。
- [ ] 验证输出节点持续反映模型计算结果，而不是离线文件中的预置值。
- [ ] 验证时间戳、周期序号、质量状态和写入生效周期。
- [ ] 建立自动化回归测试，覆盖正常写入、越权写入、类型错误、范围错误、连续写入和客户端断连。

**验收标准**

必须通过“OPC UA Client 读取过程量 → 写入控制量 → Runtime 接收并更新模型输入 → 后续模型计算产生变化 → OPC UA Client 读取到新过程量”的完整闭环测试。

## 5. P1：Runtime 运行监控与维护能力

这些功能属于完整工具系统的可维护性能力，不作为本次专利的首要创新点，但应纳入产品建设。

### 5.1 Runtime Monitor

- [ ] 展示每个实例的启动状态、运行状态、停止状态和异常状态。
- [ ] 监控仿真周期、实际执行耗时、周期延迟和超时次数。
- [ ] 监控 CPU、内存及必要的资源指标。
- [ ] 记录 OPC UA Server 状态、客户端连接数及通信异常。
- [ ] 支持查看组件运行异常和最近错误信息。

### 5.2 报警与故障处理

- [ ] 定义 Runtime 级、实例级和组件级异常分类。
- [ ] 定义周期超时、组件计算失败、OPC UA 服务异常、配置错误等报警条件。
- [ ] 支持报警产生、确认、恢复和历史查询。
- [ ] 明确可恢复错误与必须停止实例的致命错误。
- [ ] 防止单个实例故障无边界影响其他实例。

### 5.3 历史归档与查询

- [ ] 支持按实例和变量配置历史归档。
- [ ] 记录采样时间、变量值、质量状态及必要的运行上下文。
- [ ] 支持按时间范围、实例和变量查询。
- [ ] 定义数据保留策略、归档轮转和磁盘空间保护。
- [ ] 区分实时运行归档与 Studio 主动生成的离线数据集。

### 8.3 Agent Skill

- [ ] 编写供 Agent 使用的 DataFactory Skill。
- [ ] Skill 引导 Agent 先读取产品说明书和组件清单，不凭经验臆造组件、参数或端口。
- [ ] 根据用户需求识别所需变量、特征、运行时间、采样周期及变量关联关系。
- [ ] 从完整组件集合中选择组件，而不是只围绕双水箱案例组态。
- [ ] 优先参考经典案例，再根据用户需求修改或组合；必要时从空白组态构建。
- [ ] 按 DSL v2 规则生成 YAML，不生成临时 Python/Rust 仿真程序替代 DataFactory。
- [ ] 对生成配置执行静态检查/Compiler 校验；根据错误反馈修正配置。
- [ ] 对用户需求与现有组件能力不匹配的情况明确说明缺少的组件或能力，不伪造替代实现。
- [ ] 明确 Agent 负责组态构建，DataFactory 负责标准化编译、执行和数据输出。
- [ ] 使用多个不同于文档示例的用户需求进行验证，避免 Skill 只会复现双水箱模板。

### 8.4 Agent Skill 验收

- [ ] Agent 能正确列举并使用当前完整组件库。
- [ ] Agent 能生成基础数学信号组态。
- [ ] Agent 能生成并修改双水箱组态。
- [ ] Agent 能组合多个组件构建非模板场景。
- [ ] Agent 生成的 YAML 能通过 Compiler 校验。
- [ ] Agent 生成的 YAML 能由 Studio/Fast 模式执行。
- [ ] 对缺少组件、参数错误、连接错误等情况能给出明确反馈。
- [ ] 不把未来规划能力当作现有组件能力。

## 10. 推荐实施顺序

| 阶段 | 主要工作 | 阶段出口 |
|---|---|---|
| Phase 0 | 架构盘点、组件盘点、专利特征映射 | 明确现状、边界和接口 |
| Phase 1 | 共享 Engine、双时间机制 | Studio/Fast 与 Runtime/Realtime 共享执行核心 |
| Phase 2 | Runtime CLI、多 YAML 实例管理 | 脱离 Studio 独立运行 |
| Phase 3 | OPC UA Server、变量映射、闭环写入 | 外部推理系统可双向交互 |
| Phase 4 | Monitor、报警、历史归档 | Runtime 可维护、可追溯 |
| Phase 5 | 产品说明书、经典案例、Agent Skill | Agent 可基于完整组件库构建合法组态 |
| Phase 6 | 自动化验证、性能测试、专利证据整理 | 形成可复现的完整实施例 |

## 11. 明确不作为本轮核心目标的事项

- 不为了专利引入没有实际测试价值的通用插件框架。
- 不要求新增组件必须通过动态插件加载；允许按统一规范修改配置定义、Compiler 和 Engine。
- 不让 AI Agent 临时生成独立仿真程序代替标准 Engine。
- 不把离线数据集回放作为实时闭环仿真的核心实现。
- 不把 Monitor、报警和历史归档包装成主要专利创新点。
- 不将当前测试任务的被测算法直接放入自身的数据生成模型。
- 不在未实现、未测试的情况下，将规划功能标记为完成或写成已验证实施例。

---

**当前执行重点：** Runtime 实时调度层已进入代码实现阶段。先完成该 crate 的编译和测试验收，再实现 Runtime CLI、多组态实例管理，随后接入 OPC UA 闭环。产品说明书和 Agent Skill 仍以完整组件清单为基础，双水箱作为经典案例之一。
