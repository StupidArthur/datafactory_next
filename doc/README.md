# DataFactory 文档索引与协作约定

## 1. 分支约定

- 本仓库后续的产品设计文档、技术设计文档、实施计划、验收规范和专利工作文档，默认直接提交到 `main`。
- 除非任务明确要求隔离开发，否则文档工作不再单独创建 feature 分支。
- 其他 Agent 开始工作前，先同步 `main`，并阅读本目录下相关设计文档及 `doc/TODO.md)。
- 文档更新应保留完整内容，不覆盖无关章节；涉及实现状态时，必须区分“已实现且已验证”“已实现但未验证”“设计待实现”。
- 代码实现仍按任务需要使用分支；用户明确要求代码也直接提交 main 时再执行。

## 2. 文档目录建议

| 目录 | 内容 |
|---|---|
| `doc/` | 现有架构设计、DSL 规范、Engine 设计和跨模块技术设计 |
| `doc/product/` | 产品定位、需求规格、功能设计、用户流程、部署和运维说明 |
| `doc/engineering/` | 模块详细设计、接口协议、实现方案、测试计划和验收规范 |
| `doc/patent/` | 专利检索记录、技术特征梳理、技术交底材料、实施例映射和证据索引 |

已有文档暂时保留在当前路径，不为目录整齐而进行无必要的批量迁移。新增文档按主题放入上述目录。

## 3. 专利材料的公开范围

当前 GitHub 仓库为公开仓库，提交到 `main` 的内容任何人均可访问。

因此，专利材料提交前必须区分：

- **可公开材料**：公开专利文献检索记录、公开技术资料链接、已公开产品能力说明、非保密的工作进度和证据索引。
- **未公开发明内容**：尚未申请的核心技术方案、能够使他人实施该方案的详细技术交底、权利要求草案、未公开实施例、关键参数与实验数据。

未公开发明内容在申请前不得默认提交到本公开仓库。需要保留完整专利工作底稿时，应先使用私有仓库或其他受控存储；完成申请或明确确认可以公开后，再将适合公开的版本同步到本仓库 `main`。不要因为“文档默认提交 main”而自动公开可能影响新颖性或保密义务的内容。

## 4. 文档质量要求

- 先给出目标、范围和结论，再展开模块和细节。
- 结构应逻辑完整、层级清晰；同一层级尽量互斥且覆盖父级范围。
- 设计文档必须包含模块职责、数据流/时序、接口约束、异常行为和可执行验收点。
- 验收点应能通过操作步骤、自动化测试或可复现证据判断通过与否。
- 任何未通过实际验证的功能不得标记为已验收，也不得在专利材料中表述为已完成实施例。
